# Cloud mode

`.team/team.md` says `mode: cloud`. The team runs as Claude Code Projects threads and Codex on GitHub instead of four local clones. `TEAM.md`, the role files and the templates still hold (lanes, one story = one plan = one PR, signing, hard rails, the rulebook rule, review as a dialogue) **except where this file says otherwise**. `bin/wait-for`, `bin/po-wait`, `bin/status`, the launchers and the watchdog are not used: the platform starts, wakes and watches the sessions.

The design goal is that no step needs the human's hands, or the human's desk. The human picks outcomes and answers decision cards. Nothing waits for the human to merge: a PR on **Human-merge paths** gets a decision card, and the Judge merges on the human's yes (§ Human approval).

## Who runs what

| Role | Runs as | Writes | Never |
|---|---|---|---|
| PO + Architect | **Coordinator**: the Projects coordinator (Claude) | `.team/backlog/`, `.team/plans/`, `.team/ORDER.md` on main, and the status and `## Retro` lines in `.team/PAPERCUTS.md` (§ Routines); starts Builder and Judge threads | code, reviews, merging |
| Coder | **Builder**: one Claude thread per story; with `builder: codex` Codex writes the code from a `@codex` task and the thread drives everything else | code + tests on `feat/NNN-slug` (with `builder: codex`: the `@codex` build and fix tasks), the PR, `.team/reviews/NNN-slug.response.md`, `@codex review` requests, the plan attack request | the rulebook (unless the story's first line is `Rulebook story.`), scope, review files, merging |
| Attacker | **Codex** on GitHub (automatic review + `@codex review` requests, and the plan attack on risky stories) | GitHub reviews on the PR, plan attack findings on the story's issue | a verdict |
| Reviewer | **Judge**: one Claude thread per PR, started without the planning context | `.team/reviews/NNN-slug.md` on the PR branch, PR comments, the merge | code |
| Human | — | outcome rows in ORDER.md, answers on decision cards (including the yes that lets a human-merge PR merge) | merging by hand, unless they want to |

Two model families stay in every loop: Claude builds and judges, Codex attacks. Codex carries the review volume (every round, several angles); the Judge spends its turns on evidence and on ruling, not on re-reading every line the attackers already read. With `builder: codex`, Codex both builds and attacks, so the Judge (Claude) is the second family on that PR: on a Codex-built PR the Judge reads the diff itself and does not skip lines because the attackers already read them.

**Who builds** (`builder:` in `.team/team.md`). `builder: codex` is the default in a cloud repo that has a Codex environment (made by hand in Codex settings → Environments, one per repo): Codex writes the code from a `@codex` task on the story's issue (§ Builder, With `builder: codex`). Codex delivers a buildable diff from an issue task in about ten minutes (checked in mondmodel, 2026-10/11). `builder: claude` (the Builder thread writes the code) where the repo has no Codex environment, where Team settings chooses it, and for one story when its ORDER row says so. A direct Codex task in the browser is a manual step and is not part of this flow.

## Flow

```
outcome row → story + plan (main) → Builder thread → (plan attack on risky stories) → PR → Codex attacks → Builder answers → … → Judge → merge
```

1. **Coordinator as PO.** Takes the next row under **Kö**. A row may be an outcome ("more booked scoping calls from the site") rather than a task: then propose the stories that serve it, write the first one, and say which others you plan in the story's Log. Writes `.team/backlog/NNN-slug.md` with a filled-in `## Signal`, ticks the row, pushes.
2. **Coordinator as Architect.** Reads the code, runs the **Baseline**, writes `.team/plans/NNN-slug.md`, pushes. Too big → `verdict: needs-split` and split it yourself as PO.
3. **Coordinator starts the Builder thread** with: the repo, the story and plan paths, and "follow `.claude/skills/agent-team/team/CLOUD.md` § Builder". One Builder per story; one story in flight per repo unless the human's row says otherwise. A story is in flight until its PR is merged or closed.
3a. **Plan attack** (risky stories only). When the plan's Files name a path on **Adversarial paths** or **Human-merge paths**, or the story is a `Rulebook story.`, the Builder's first act is to ask Codex to attack the plan (§ Builder step 0), before any code is written. The Coordinator answers it as Architect: it adds `## Plan attack` to the plan with one line per Codex M and S finding, `changed in plan` or `disputed — <reason>`, changes the plan where a finding holds, pushes to main, and tells the Builder to go. Other stories get no plan attack.
4. **Builder** (below) opens the PR, or has Codex open it with `builder: codex`, and drives it through Codex rounds until no Must fix is open and CI is green, then asks the Coordinator for a Judge.
5. **Coordinator starts the Judge thread** with only: the repo, the PR number, and "follow `.claude/skills/agent-team/team/CLOUD.md` § Judge". No summary of the plan or of the Builder's work: the Judge reads the files.
6. **Judge** (below) rules. `request-changes` goes back to the Builder thread, which wakes on the PR comment. `approve` → merge or hand to the human. `escalate` → the Coordinator writes the Operatör line and puts the dispute to the human as a decision.
7. **After merge** the Coordinator checks the story's `## Signal` when it can be read (the next routine run at the latest) and writes one line in the story's Log: seen, not seen, or not yet measurable.

## Builder

0. **Plan attack** (only when § Flow 3a applies). Open the story's issue `NNN: <story title>` if it does not exist (with `builder: codex` it is the same issue that later carries the build task; post the build task only after this step) and comment: `@codex attack the plan: read .team/plans/NNN-slug.md against .team/backlog/NNN-slug.md, AGENTS.md and the code it names. Do not write code and do not open a PR. Find wrong facts, missing cases and failure paths, acceptance criteria the plan does not meet, and scope the story did not ask for. Number findings M/S/N with file:line or plan section.` Issue replies do not wake you (a PR watch covers PRs only), so after posting, schedule one reminder about 15 minutes after the request and one at the hour (§ Quota, issue tasks); at each, read the issue. When Codex has answered, message the Coordinator `NNN plan attack: <n> findings, <issue link>`. Start building when the plan's `## Plan attack` answers every M and S finding and the Coordinator says go. If Codex replies with an error, request the attack once more. If it fails twice, or has not answered an hour after the request, tell the Coordinator, who notes that under `## Plan attack` in the plan, and build the plan as it stands. You never edit the plan.
1. Branch `feat/NNN-slug` from main, push it at once. Read the story, the plan, `AGENTS.md`, `TEAM.md` and `roles/coder.md` (that file holds, with this section winning where they differ).
2. Build the plan with tests. Run **Test before commit** before every push. Open the PR **as a draft**: title `NNN: <story title>`, body as in `roles/coder.md`, plus one line per acceptance criterion saying how it was shown. It stays a draft through the Codex rounds (step 5 marks it ready), so the repo's CI runs its full gates once per story instead of on every fix push (§ Quota, Actions minutes).

   **With `builder: codex`** Codex does step 2 and every code fix; you do the rest of this section.
   - Open the story's issue `NNN: <story title>` with a body that is the `@codex` task; if the issue already exists from step 0, post the task as a new comment on it instead (editing the body does not start Codex): `@codex build .team/plans/NNN-slug.md for .team/backlog/NNN-slug.md. Follow AGENTS.md. Run Test before commit. Open a draft PR titled NNN: <story title> from feat/NNN-slug, body as in roles/coder.md with one line per acceptance criterion. Sign — Coder (Codex) on behalf of <human>.`
   - Issue replies do not wake you: schedule one reminder about 15 minutes after the request and one at the hour. At each, read the issue and look for a PR titled `NNN:`; once there is one, watch it like your own. No reply and no PR an hour after the request counts as a failed task.
   - If Codex returns a diff and no PR, apply it unchanged on `feat/NNN-slug`, push, and open the PR yourself as in step 2.
   - Ask Codex for each fix with a `@codex` comment on the PR naming the finding (`@codex fix M2: <one line>`). Do not write the fix yourself while Codex can.
   - Run **Test before commit** yourself on Codex's head before every review request and before you ask for a Judge.
   - If Codex fails the same task twice (an error reply, no PR or diff, or a head that fails **Test before commit**), build that task yourself and write `Codex failed twice on <task>; built by the Builder thread` in the response file.
3. **Request Codex.** Codex reviews on its own only when a PR is opened for review or a draft is marked ready, never on a later push (checked 2026-10-24). So post `@codex review` yourself: once when the PR opens (always, also on a draft), and once after every push that changes code, followed by the focus for that round (the findings you answered, the files you changed). Codex reacts 👀 while it runs and 👍 when it has no findings. If the diff touches **Adversarial paths** in Team settings, the first round also gets three separate comments, one per angle:
   - `@codex security review` (Codex's own security review).
   - `@codex review — security: authorization, input validation, secrets, data exposure. Number findings M/S/N with file:line.`
   - `@codex review — failure paths: errors, empty and malformed input, concurrency, retries, rollbacks. Number findings M/S/N with file:line.`
   - `@codex review — story fit: does the diff meet every acceptance criterion in .team/backlog/NNN-slug.md, and does it do anything the story did not ask for? Number findings M/S/N with file:line.`
   If the PR carries a data change (§ Data changes), every Codex round on it also gets the fact angle from that section.
   If a Codex review fails (quota, an error reply), request the same review once more before anything else. A review that fails twice, or has not finished long after the request, is said in the response file; whether the rounds may then go on without Codex is the project's call in Team settings, and never for a data change.
4. **Answer every Codex finding** that is a P0/P1 or numbered M/S, in `.team/reviews/NNN-slug.response.md` (`## Codex round N — YYYY-MM-DD`, one line per finding: `fixed in <sha>` or `disputed — <reason>`). Codex is an attacker, not an authority: dispute what is wrong, with a reason the Judge can check. Never change code only to make a finding go away.
5. **Stop the rounds** when every Codex review you requested for the current head commit has finished (a review posted on that commit, or Codex's 👍 on your request), none of them raises a new P0/P1 or Must fix, and every earlier finding is answered. A review still running (👀) means wait for it: its result wakes you. Three Codex rounds without getting there is also a stop: say so. Then mark the draft ready (`gh pr ready <n>`; where GraphQL is blocked, as in cloud sessions, the REST route the 403 names). Marking it ready starts the full CI gates (given the `ready_for_review` type, § Quota, Actions minutes) and a Codex review of its own; that review counts as a current-head review you wait for and answer. Wait for both (their results wake you). In a repo with `runner: mini`, a required check still queued after **Runner offline after** means the runner is offline (§ Quota, Runner offline). If a required check fails, fix it, push, and request one Codex round on the fix; the PR stays ready. Message the Coordinator only when, on the current head, every Codex review (requested or started by marking ready) has finished with no new P0/P1 or Must fix, every finding is answered, and every required check has **run** after ready and passed: a `skipped` job reports success but proves nothing, so a required check whose last run on the head was skipped is not green. The one exception is a skip by the repo's own change classifier (for example a docs-only or board-only diff): it counts as green when the classifier job itself ran after ready and succeeded, the skip follows from its output, and every piece of code the skipped gate covers had that gate run after ready and pass, on this head or on an earlier head the classifier compared against. A diff with no code at all (docs-only or board-only from the start) needs no earlier run. A skip that rests on an earlier skip, or on a run from before ready, does not count, and a skip caused by the draft guard never counts. `NNN ready for judge: PR #<n>, <rounds> Codex rounds, <open disputes or "no open disputes">`.
6. **On `request-changes` from the Judge** (you wake on the comment): answer every Judge M and S in the same response file under `## Judge round N`, fix, push, request one Codex round on the change, and message the Coordinator again only when step 5 holds for the new head.
7. End your watch when the PR is merged, closed without merge, or the Judge escalates.

## Judge

1. `gh pr checkout <n>`. Read the story, the plan, `AGENTS.md`, `roles/reviewer.md` and the review checks it names. You were started without the planning conversation on purpose: do not ask for it.
2. Run every **Test before commit** check yourself, and the screenshots, previews or queries Team settings names. On a data change, also check § Data changes: the Codex review (with the fact angle) finished on the last commit that changed anything outside `.team/reviews/**`, and every open row in the package's own review file is fixed or ruled `not valid` by you. Check that every required check on the head has run after the PR was marked ready and passed (not `skipped`, except a change-classifier skip as § Builder 5 allows); one that did not is a Must fix. **Every acceptance criterion gets evidence** in the review file: a test name and its result, a command and its output, or a screenshot. A criterion you could not show is a Must fix, or an Operatör line if only the human can show it.
3. **Rule on Codex.** List every Codex finding the Builder answered, with your ruling: `valid — fixed`, `valid — still open` (becomes your Must fix), or `not valid — <one sentence>`. Do the same for the Builder's disputes. Then try to break what the attackers did not cover; you do not need to re-read lines they already read unless you doubt them, except on a Codex-built PR (`builder: codex`), where you read the whole diff yourself.
4. Write `.team/reviews/NNN-slug.md` from the template, `verdict:` as in `roles/reviewer.md`. Commit it to the PR branch, push, and post it as a PR comment (`gh pr review <n> --comment --body-file …`).
5. **On approve:** if `.team/team.md` says `merge: auto`, the diff touches no **Human-merge paths** and the story is not a `Rulebook story.`, merge with `gh pr merge <n> --squash --delete-branch` (never `--admin`). Your own review commit may start new checks: if required checks are pending, use `gh pr merge <n> --auto --squash --delete-branch` so GitHub merges when they pass; where auto-merge is not enabled for the repo, keep watching and merge when the checks' result wakes you. Pending checks are never a reason to hand the PR to the human. A failing check or a conflict with main goes back to the Builder as `request-changes` with that one Must fix. Only a diff on **Human-merge paths**, a `Rulebook story.` (always, whatever **Human-merge paths** lists), or `merge: human` waits for the human: message the Coordinator `NNN approved, needs the human: <which path or rule>`, keep your watch, and merge as in § Human approval when the human's yes reaches you. This step replaces `roles/reviewer.md` step 6 in cloud mode.
6. **Escalate** as in `roles/reviewer.md`: a Must or Should fix still disputed after your third round. Message the Coordinator.
7. You hold one PR. Stop when it is merged, closed without merge, handed to the human, or escalated.

## Data changes

Codex finds fact errors that tests and the other reviews miss, so data and content get the same attack as code before they reach production. **Data changes** in Team settings says what counts in the project; if the line is missing, this section still holds for the general case: any package (SQL, JSON, CSV or a script's input) that writes to production data, and any PR that exports production content into the repo.

1. **No write before review.** A data package is never run against production until the exact files the operator will run (the apply file, its rollback, and the source data it was built from) have been on a PR, the Codex review of the last commit that changed any file outside `.team/reviews/**` has finished, and every Codex P0/P1 or M/S finding and every open row in the package's own review file is fixed or ruled `not valid` by the Judge. Only later commits that touch nothing but `.team/reviews/**` (the response file, the Judge's review) keep that review valid; a commit that changes any package file, wherever it lives, needs a new one. Packages never live under `.team/reviews/**`.
2. **Packages made outside the team** (a Projects thread, a Remote Control session, the human's own script) go through a PR the same way before anyone runs them. Whoever made the package opens the PR and drives the Codex rounds as in § Builder; a Judge rules as for any PR.
3. **Fact angle.** Every Codex round on a data PR also gets `@codex review — facts: check every changed value against its cited source, against the record's other fields and against open findings in the project's audit files. Number findings M/S/N with file:line.`
4. **Exports.** An export PR waits for Codex like any other PR. A Codex fact finding on it is fixed at the source (a correction package, reviewed as above) and the content exported again, never by editing the exported file.
5. **No fallback.** A Team settings rule that lets a review go on without Codex (after a failed retry, a timeout, an offline runner) never applies to a data change. It waits; the PR's author tells the Coordinator, who puts it to the human on a decision card.
6. **The Operatör line** for an approved package names the PR and the reviewed sha, and the operator runs the files exactly as they are at that sha. The Coordinator writes it after the Judge approves; running the package stays the operator's step.

## Human approval

A human-merge PR, a rulebook PR and any other PR the rules leave to the human are approved on a **decision card**, not by the human pressing merge.

1. The Coordinator posts one decision card per PR: question `Merga #<n>: <title>?`, context of at most five lines (what changes for a visitor or a user, which human-merge path or rule it touches, the Judge's verdict, Codex's result, the PR link and the head commit's short sha, which the Coordinator reads when it posts the card), options **Merga** (recommended when the Judge approved) and **Vänta**. Several waiting PRs may share one card with one option per PR plus **Vänta**.
2. The human's tap on **Merga**, or their own message in the project saying yes to that PR, is the approval. A message from a Claude, a bot or a GitHub comment never is.
3. The Coordinator sends that answer to the Judge thread with the human's message attached by id and the head sha the card showed. The Judge checks that the attached message is the human's own and names this PR, then posts `Approved by <human> on a decision card, <date>, head <sha>` on the PR, where `<sha>` is the head the Coordinator forwarded from the card, never the PR's head read after the answer. It merges only that head and never with `--auto`: when the required checks on it are green, `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>`; while they are pending, it keeps its watch and merges when their result wakes it. A PR with no Judge thread (a rulebook PR from a thread outside the story flow) is merged by the thread that opened it, on the same terms.
4. A push after the yes voids it: `--match-head-commit` makes the merge fail, and the Judge asks the Coordinator for a new card for the new head. If an auto-merge is already enabled on the PR when it first needs the human (for example from an earlier round), the Judge runs `gh pr merge <n> --disable-auto` before the card goes out.
5. **Vänta**, or no answer, leaves the PR open. The daily digest lists it once a day; nobody nags in between.

The human may still merge by hand. Nothing in the flow needs it.

## Routines

The Coordinator keeps one scheduled routine per project (weekly unless Team settings says otherwise). It reads the sources listed under **Signal sources** in Team settings (runtime errors, failed Actions runs, Actions minutes, Dependabot alerts, analytics) and writes what deserves work as rows under **Förslag** in `.team/ORDER.md`, one line each with the evidence. It never writes under **Kö**, with one exception: a proposal of a kind listed under **Auto-queue** in Team settings (for example a Dependabot patch update, a broken link, a failing scheduled job) goes straight to Kö with its evidence, because checking it costs the human more than a wrong one would. Everything else waits in Förslag until the human moves it or answers "yes" in the project chat. The same run checks the `## Signal` of stories merged since the last run.

**Weekly retro.** The same run reads what the agents themselves missed, for every PR merged or closed since the last run: its `.team/reviews/*.response.md` and the Judge's review file (on the PR branch if it closed unmerged), escalations (`verdict: escalate`), failed `@codex` tasks and reviews the response file reports, and `.team/PAPERCUTS.md` (lines since the last run and every line still `open`). Agents write papercuts per `AGENTS.md` § Papercuts.
- It groups them into patterns: the same kind of failure, or the same kind of finding the Builder missed (a Codex or Judge finding the response file answers `fixed`). A pattern seen at least twice, or once if it caused a revert or a wrong merge, gets one row under **Förslag**: `Retro: <pattern> → <proposed change> in <file to touch> — <evidence links>`. A pattern that already has an open row gets the new links on that row, not a second row. A change to the rulebook names the rulebook file; on the human's yes it becomes a `Rulebook story.` for agent-team. Retro rows never go to Kö, whatever **Auto-queue** says, and the routine never edits the rulebook, `AGENTS.md` or a role file itself.
- It appends one line under `## Retro` in `.team/PAPERCUTS.md` (create the file from `assets/team/PAPERCUTS.md` if missing), so the trend stays in the repo: `YYYY-Www | Codex fixed <n> | Judge fixed <n> | failed @codex tasks <n> | escalations <n> | papercuts open <n>`.
- It closes the loop: papercuts behind a new row get `proposed <date>`; when the PR from that row merges, `fixed <PR link>`; when the human drops the row, `open` again.
- The digest gives the retro one line (the `## Retro` line and the number of new rows), none in a week with no new row and all counts zero.

## What reaches the human

Reading agent output is where the human's time goes, and an agent waiting for a human is an agent doing nothing. So:

- No step waits for the human except a decision card (a decision with a recommendation, or the yes on a human-merge PR) and a Förslag row outside Auto-queue. Everything else proceeds and is reported after. Nothing needs the human at a computer: every wait is a card they can answer from the phone.
- One digest, not a stream: the Coordinator sends one short message per day with activity (merged, waiting on the human, escalated), and nothing on quiet days. Builder and Judge do not message the human.
- Every item that needs the human says, in its first line, what to decide or do and what happens if nothing is done.

## The human's taste

`skills/distill-feedback` turns the human's past feedback (PR comments, closed-unmerged PRs, ORDER rows, decisions in handoff notes) into a list of principles in the project's `REVIEW.md`. The Judge reads `REVIEW.md` through **Review checks**. Run it when a project starts cloud mode and again when the human has corrected the team several times on the same kind of point. Changing `REVIEW.md` is a rulebook change: the human approves the list.

## Quota

- Codex carries the review volume. Claude turns go to building and to the Judge's evidence and rulings.
- The Coordinator plans at normal effort and does not watch PRs. Builder and Judge watch only their own PR and stop as above.
- One `@codex review` comment per Builder push round, plus the three angles once on adversarial paths and the fact angle on every round of a data PR. No re-pinging the same commit, except the one retry after a failed review.
- Codex builds where `builder: codex`, so Claude turns on such a story go to driving the PR, the evidence and the ruling. The plan attack is one `@codex` task per risky story (§ Flow 3a), with no re-ping except one retry.
- **Actions minutes.** In a private repo every CI job bills at least a whole minute, and a full gate set costs 10–15 minutes per push (mondmodel, 2026-11: 2 922 minutes in three days, of which about 80 % on PR pushes during fix rounds). So a PR is a draft while Codex attacks it, and the repo's workflows skip their heavy jobs on drafts (`if: github.event.pull_request.draft != true`) and list `ready_for_review` in their `pull_request` types (`types: [opened, synchronize, reopened, ready_for_review]`; the default types leave it out, so without it marking the PR ready starts nothing); they run when the Builder marks it ready (§ Builder step 5). Before the PR is ready, the Builder's own **Test before commit** is the gate. A repo that adds a workflow keeps both the draft guard and the `ready_for_review` type on every workflow with a job that installs dependencies.
- **Self-hosted runner.** A private repo with `runner: mini` in `.team/team.md` runs its CI on a self-hosted runner on the Mac mini instead of on GitHub-hosted minutes (setup and rules for the human: `team/RUNNER.md`). Never on a public repo: anyone who can open a PR there could run code on the mini. One runner per repo, each in its own isolated Linux VM that cannot see the Mac's or the other VMs' files (service containers need Linux), one job at a time, under its own macOS account. Every job picks it with `runs-on: ${{ fromJSON(vars.RUNS_ON || '["self-hosted","mini"]') }}`; the draft guard and the `ready_for_review` type stay as above. Each job starts from a clean workspace, and the runner's cleanup hook removes credential files, containers and volumes (named ones too) after it, so no secret a job used stays on the mini. The only secret kept there is the runner's own identity key, which serves that one repo and is revoked by removing the runner (`team/RUNNER.md` § Rules). Cost: self-hosted minutes in private repos are free as of 2026-11-06 (GitHub announced $0.002/min from 2026-03-01 and postponed it on 2025-12-17 with no new date); where Actions minutes are a **Signal source**, the routine rechecks GitHub's Actions pricing page.
- **Runner offline.** A job on the `mini` label that no runner picks up stays queued (GitHub fails it after 24 hours). When the Builder marks a PR ready, or pushes after ready, in a repo with `runner: mini`, it schedules one reminder after **Runner offline after** (Team settings, default 30 minutes). If a required check is still queued then, it messages the Coordinator `NNN runner offline: <n> jobs queued since <time>`, and the Coordinator puts it to the human on a decision card: **Vänta** (recommended; the jobs start when the mini is back) or **Kör på GitHub-hosted** (the card says it spends the account's minutes, and fails while the Actions budget is $0). On the second, the human sets the repo variable `RUNS_ON` to `"ubuntu-latest"` (an Operatör line: repo variables need admin rights), the Builder cancels the runs still queued for `mini` (a variable change does not move a queued job, and a run cannot be re-run until it has finished: `gh run cancel <id>`, then check that it reads `cancelled`) and starts fresh runs that read the new variable by converting the PR to draft and marking it ready again (the ready review Codex then posts is answered as in § Builder 5), and after the merge the Coordinator writes the Operatör line to delete `RUNS_ON` again. A data change (§ Data changes) never merges with a required check unrun: it waits for the runner or for the human's choice.
- No polling loops. Threads wake on PR events and on messages. The one exception is an `@codex` task on an issue (plan attack, build task), which wakes nobody: the Builder schedules two reminders per task (about 15 minutes, and the hour), no more.

## One-time setup per repo (human)

1. Codex: connect the repo, and turn on automatic code review for it (Codex settings → Code review).
