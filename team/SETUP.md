# Setup and walls in full (human)

`CLOUD.md` holds the rules every thread reads each turn. This file holds what only the human does, once per repo, and the full text of each wall in `CLOUD.md` § Walls, moved here unchanged in v0.8.0 so the per-turn file stays short. Every condition below binds as if it stood in `CLOUD.md`; where the two differ, the stricter one holds. Every step is an **Operatör** step: only the human does it.

## One-time setup per repo

1. Codex: connect the repo, and turn on automatic code review for it (Codex settings → Code review).
2. Codex: create an environment for the repo (Codex settings → Environments) so `@codex` tasks can run; then the repo can use `builder: codex`.
3. Paste `assets/cloud/project-instructions.md` (filled in) as the project's instructions.
4. In the repo: `.team/team.md` gets `mode: cloud`, `builder: codex` once the Codex environment exists (else `builder: claude`), and a `merge:` line; `AGENTS.md` gets the cloud settings (including **Data changes**) and `## Code Review Rules` from `assets/root/AGENTS.md`.
5. Private repo with its own CI on the Mac mini: set up the runner per `team/RUNNER.md`, then `runner: mini` in `.team/team.md` and `runs-on` as in `CLOUD.md` § Quota in every workflow. Public repos stay on `runner: github`.
6. The main ruleset (§ Walls in full below), as the human on their own admin login, never with a token in a session: fill in the required checks in `assets/cloud/main-ruleset.json` (or delete that rule, § Walls in full below) and run `gh api -X POST repos/<owner>/<repo>/rulesets --input main-ruleset.json`; or click Settings → Rules → Rulesets → New branch ruleset: name `main: PR only`, Enforcement Active, no bypass, target the default branch, then Restrict deletions, Require a pull request (0 approvals, merge method Squash), Require status checks (the always-running jobs), Block force pushes, Create. The Coordinator writes this as an Operatör row per repo and checks it afterwards with `gh api repos/<owner>/<repo>/rules/branches/<branch>`.
7. The deny list from `assets/root/.claude/settings.json` in the repo's `.claude/settings.json`, and `.claude/settings.json` on **Human-merge paths**. Where `AGENTS.md` lets board files go straight to main, that line changes to board PRs in the same PR.
8. The merge workflow (§ Walls in full below): `assets/root/.github/workflows/agent-team-merge.yml` into the repo's `.github/workflows/` (with `runs-on` as in `CLOUD.md` § Quota under `runner: mini`), and `.github/workflows/agent-team-merge.yml` on **Human-merge paths**; the repo variables `AGENT_ACCOUNT` once there is one and `AFTER_MERGE_WORKFLOWS` if a workflow must run on main after a merge (Operatör lines: repo variables need admin rights). Its install PR is the one merge the workflow cannot do yet: it needs the human's yes naming that PR (one message may name several).
9. **Stories in flight: 2** (`CLOUD.md` § Flow 3) also needs `strict_required_status_checks_policy: true` in the ruleset's required-status-checks rule, set as in step 6.

## Walls in full

What the rules forbid is also blocked by settings, so a step that goes wrong stops at GitHub instead of reaching main.

- **Main ruleset.** Every team repo's default branch has one branch ruleset, `main: PR only`, with an empty bypass list (nobody, admins included): changes only by PR (0 approvals, squash only), the repo's required checks green, no force-push, no deletion. A ruleset, not classic protection: it works on private repos with GitHub Pro, and agents can read it (`gh api repos/<owner>/<repo>/rules/branches/<branch>`). Required checks name only jobs that run on every PR, board-only diffs included (a change classifier or gate job): a required check from a workflow skipped by a path filter stays pending and blocks every merge. A repo without such a job gets the ruleset without required checks and a Förslag row to add one. A private repo whose CI cannot run (no Actions minutes, no `runner: mini`) adds the required checks when its CI runs again, the rest at once. Setting or changing the ruleset is the human's (an Operatör row, § One-time setup per repo below); no agent changes it.
- **Board PRs.** Wherever `CLOUD.md` has the Coordinator write or push board files on main (`.team/backlog/`, `.team/plans/`, `.team/ORDER.md`, the Coordinator's lines in `.team/PAPERCUTS.md`), it does so by a board PR: a branch `board/YYYY-MM-DD-<slug>`, a PR titled `board: <what>`, one per Coordinator turn rather than one per file. The Coordinator reads the PR's head sha, lists that head's changes with renames off (`git diff --no-renames --name-only origin/<default>...<sha>`, so a rename's source and every deletion count), and when every path is a board file and the required checks pass on that head, starts a Judge thread for it (the repo, the PR number, "follow `CLOUD.md` § Judge"), and the Judge merges it with the head pinned as `CLOUD.md` § Judge 0 says. No `@codex review` (Codex's automatic review may still run; nobody waits for it), no review file, never a decision card, whatever `merge:` or **Human-merge paths** say, and a board PR does not count toward a repo's cap on open PRs. The Coordinator never merges. A board PR whose diff holds anything else is closed and the change goes through the story flow.
- **Merge workflow.** No agent session runs a merge. Claude's cloud sessions stop an agent's own `gh pr merge` unless the human's yes names that PR, which is the per-PR wait `CLOUD.md` § Human approval removed (seen on agent-team #17 and #18 and relationsmodellen-site #48, 2026-11-07), and a repo's `permissions.allow` cannot lift that in a project with more than one repo. So the merge is GitHub's: every team repo carries `.github/workflows/agent-team-merge.yml` from `assets/root/`, and whoever `CLOUD.md` says merges (the Judge in `CLOUD.md` § Judge 0 and 5 and § Human approval 4) asks for it with a PR comment whose own line reads `agent-team-merge: <40-hex head sha>`. The workflow runs from the default branch's copy (a PR cannot change the rule it is merged under) and checks out no code. It acts only on a comment by the repo owner or the `agent-account:` login (repo variable `AGENT_ACCOUNT`), and merges (squash) only when the PR is open, not a draft and its head is the pinned sha; outside `board:` PRs, a repo with `.team/` must also have a review file in the PR with `verdict: approve` at that sha, and every PR needs a Codex comment or review. The ruleset still decides the rest: GitHub refuses the merge while a required check is not green. It then deletes the branch, dispatches the workflows named in the repo variable `AFTER_MERGE_WORKFLOWS` (a merge by the workflow's token starts no `push` workflow, so a workflow that must run on main gets `workflow_dispatch:` and a place in that list), and comments `Merged by agent-team-merge: head <sha>`; when it does not merge it comments why, which wakes the Judge's watch. A Judge that has seen neither comment 15 minutes after asking messages the Coordinator `NNN merge workflow did not run`; the Coordinator checks the run (no runner, no minutes) and writes the Operatör line or the runner card (`CLOUD.md` § Quota). These checks are a floor, not the Judge's review: when to ask stays `CLOUD.md` § Judge 5's rule. The workflow file is on **Human-merge paths**.
- **Deny rules.** The repo's `.claude/settings.json` carries the deny list from `assets/root/.claude/settings.json`, merged into an existing file, never replacing it: pushes to `main`/`master`, force-pushes (`--force*`, `-f` alone or in the usual groups `-uf`, `-vf`, `-qf`, `-nf`, `-uvf`, `+<ref>`, `--mirror`), `gh pr merge --admin`, and `gh api` calls on branch protection or rulesets (agents read the rules through `rules/branches`, which the list does not match). Deny wins over allow in every settings scope, so it holds for every Claude session in the repo, the human's own included. It stops the usual form of a command, not every spelling (`git -C . push` passes it): the ruleset is the wall, the deny list the early stop. `.claude/settings.json` is on **Human-merge paths**.
- **Agent account** (optional). A GitHub machine user for the agents (GitHub's terms allow one, owned by the human), a collaborator with the **Write** role on each team repo: it can push branches, open and merge PRs the ruleset lets through, and comment, but cannot change settings or rulesets. Its token is classic (`repo`): a fine-grained token cannot reach repos where its user is a collaborator on a personal account (GitHub docs, 2026-11), so the Write role is the limit. The token lives only where an agent runs as that account (the mini's Keychain for Codex CLI), never in a repo, the rulebook or a cloud environment. Creating and inviting the account is an Operatör row; `.team/team.md` then names it in `agent-account:`. From then on what that login does on GitHub is the agents', and the human's login means the human's own act. Signing stays `— <Role> (<model>) on behalf of <human>`, a PR with an exception in § Human approval is still approved on a decision card (not a GitHub review), and the bypass list stays empty. Cloud threads act through the Claude GitHub App on the human's login until a thread can take another identity: for them nothing changes yet.
